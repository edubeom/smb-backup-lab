## 01. AI와 만드는 서버 백업 기록이 복구의 근거가 되다 · 00:00 · 40초

안녕하세요. 오늘은 AI와 함께 SMB 공유에 서버를 백업하는 도구를 만든 과정을 소개합니다. 중심 주제는 dev-process-light입니다. 코드를 빨리 만드는 장면보다, 무엇을 원했고 무엇을 확인했으며 다음 사람이 어디서 이어갈 수 있는지 기록하는 과정을 보여 드리겠습니다. 실제 서비스를 유지하며 진행한 사례이고, 확인한 결과와 아직 남은 시험을 나눠 설명하겠습니다.

## 02. 오늘 가져갈 세 가지 · 00:40 · 30초

이 강의에서 가져갈 것은 세 가지입니다. 첫째는 작업을 작은 단위로 정리하는 방법입니다. 둘째는 성공했다는 말 대신 실제 검증 범위를 적는 방법입니다. 셋째는 기록과 Git, 중간 화면을 다음 작업의 출발점으로 사용하는 방법입니다. 백업 경험이 적어도 흐름을 따라올 수 있도록 실제 사례를 단순한 그림으로 설명하겠습니다.

## 03. 시작은 “어디에 무엇이 있지?” · 01:10 · 45초

처음부터 압축 명령을 실행하지 않았습니다. 서버에는 프로젝트 외에도 데이터베이스와 메일, SSH와 터널 설정이 있었습니다. 실제 위치와 기존 백업을 먼저 조사해야 복구할 때 빠뜨리지 않습니다. 이 단계의 원본 조사에는 서버 식별 정보가 들어가므로 방송에서는 지금처럼 범주만 보여 줍니다. 조사와 공개 자료를 구분하는 것도 기록의 한 부분입니다.

## 04. dev-process-light는 작업 방법을 남깁니다 · 01:55 · 50초

dev-process-light는 AI와 작업할 때 따를 규칙과 스킬, 기록 형식을 프로젝트 안에 둡니다. 새 대화에서는 현재 상황을 읽고, 만들기 전에는 목표와 완료 기준을 적고, 만들고 나서는 직접 확인한 범위를 기록합니다. 이번 백업 도구는 이 방법을 실제로 적용한 사례입니다. 사용한 버전을 고정해 두었으며 원본 저장소의 최신 내용과 차이가 있을 수 있다는 점도 자료에 적었습니다.

## 05. 일곱 스킬을 필요할 때 사용합니다 · 02:45 · 55초

설치한 light 스킬은 일곱 가지입니다. 모두를 매번 실행하는 것은 아닙니다. 작업 시작과 합의, 확인과 저장을 중심으로 필요한 설명서와 기록 보기를 이어갑니다. 이 사례에서는 기록 포털을 따로 만들지 않았고 되돌리기도 실행하지 않았습니다. data-light는 별도의 짝 스킬로 설치했지만 새 업무 데이터 모델을 만드는 일이 아니어서 적용하지 않았습니다. 백업 메타데이터와 업무 데이터 설계를 구분했습니다.

## 06. 시작 → 합의 → 확인 → 저장 · 03:40 · 45초

전체 흐름은 네 단계로 기억하면 됩니다. 시작할 때 읽고, 만들기 전에 합의하고, 확인한 뒤에 저장합니다. 기존에 사용자가 승인한 범위는 같은 질문을 반복하지 않고 이어갑니다. 반면 서비스 중단이나 기존 백업 삭제처럼 별도 확인이 필요한 경계는 계속 지킵니다. 작은 수정부터 이 흐름을 반복하면 다음 세션에서 이전 결정을 추측할 필요가 줄어듭니다.

## 07. 요구를 작업 카드로 바꿉니다 · 04:25 · 55초

요구를 그대로 긴 대화에만 두면 무엇이 완료인지 흐려집니다. 그래서 목표, 눈으로 확인할 완료 기준, 영향받을 기능과 설명서를 작업 카드로 정리했습니다. 사용자의 매일 한 번, 최근 성공 다섯 개, 비밀은 Git 밖이라는 요구를 실패 조건과 보관 조건으로 옮겼습니다. 이미 승인한 진행 범위를 기록한 덕분에 같은 허락을 계속 묻는 것도 피할 수 있습니다.

## 08. 기록은 세 층으로 읽습니다 · 05:20 · 45초

기록이 길어져도 전부 다시 읽지 않도록 세 층으로 나눴습니다. 먼저 전체 흐름에서 필요한 날짜를 찾고, 목록에서 작업 번호를 보고, 필요한 상세만 엽니다. 지금 상태는 NOW, 기능과 파일 연결은 FEATURES, 선택의 이유는 DECISIONS에 남깁니다. 이 자료를 만드는 시점에도 이전 작업을 이 순서로 읽고 이어갔습니다. 기록을 많이 남기는 것과 찾기 쉽게 남기는 것은 함께 가야 합니다.

## 09. 18개 단계가 한 흐름으로 남았습니다 · 06:05 · 45초

처음 여섯 단계에서는 규칙을 설치하고 기반 도구를 만들었습니다. 이후 공유기 연결 오류를 해결하고, 프로젝트별 파일과 중단 없는 메일 수집으로 요구를 구체화했습니다. 첫 실제 백업 뒤에는 데이터베이스 복원과 외부 키 확인을 진행했습니다. 마지막에는 자동 실행과 설정 호환, 승인 입력의 사용성까지 다뤘습니다. 각 화면은 그 단계에서 만든 공개용 진행 카드이며 실제 서버 화면 녹화와 구분합니다.

## 10. SMB 공유에 암호화 파일을 보관합니다 · 06:50 · 50초

구조는 Linux 서버에서 필요한 자료를 전용 도구로 수집한 뒤, 암호화해서 SMB 공유에 보내는 방식입니다. 실제 배포에서는 공유기 외장하드를 목적지로 사용했습니다. 인증과 암호화 키는 서버의 보호된 경로에 두고 Git에는 넣지 않습니다. 현재 사례는 SMB 공유를 대상으로 구현되어 있습니다. 서버 전체의 부팅 가능한 디스크 복제와는 복구 목표가 다르다는 점도 설명서에 적었습니다.

## 11. 프로젝트마다 필요한 파일만 꺼냅니다 · 07:40 · 45초

프로젝트를 하나의 거대한 파일에만 넣지 않고 디렉터리별로 나눴습니다. 그림의 프로젝트 이름은 만든 예시입니다. 시스템 설정과 데이터베이스 덤프도 별도 파일로 저장합니다. 모든 구성요소가 검증된 뒤 하루 성공 묶음 하나로 기록하며 필요한 프로젝트나 구성요소를 골라 복원할 수 있습니다. 파일이 나뉘어 있다는 것과 성공 기준이 나뉘는 것은 구분했습니다.

## 12. 검증이 끝나야 그날의 성공입니다 · 08:25 · 55초

전송이 끝났다는 것만으로 성공 처리하지 않습니다. 올바른 CIFS 공유인지 확인하고 수집한 뒤 암호화하여 전송합니다. 전송본을 다시 읽어 해시와 복호화를 확인한 다음에야 성공 기록을 만듭니다. 새 성공본이 검증된 뒤 승인된 범위의 오래된 성공본을 정리합니다. 공간이 없거나 실패하면 기존 성공본부터 지우지 않습니다. 실패 조각과 다른 프로그램의 자료도 자동 정리 범위에 넣지 않았습니다.

## 13. 오류 22를 암호 문제로 단정하지 않았습니다 · 09:20 · 60초

첫 실제 문제는 SMB 연결 오류였습니다. 처음에는 안내가 인증 문제처럼 보여 사용자가 암호를 반복 입력했습니다. 오류 번호와 협상 결과를 확인하니 이 공유기에서 필요한 버전 설정을 맞추지 못한 문제였습니다. 이 사례에서는 vers 2.0 설정으로 연결됐습니다. 모든 SMB 서버에 같은 버전을 권장한다는 뜻은 아닙니다. 같은 입력을 반복하기 전에 원인을 조사한다는 규칙이 실제로 필요한 순간이었습니다.

## 14. “메일 중단 없이 진행하고 싶습니다” · 10:20 · 55초

사용자는 메일을 중단하지 않고 싶다고 했습니다. 그러면 처음 만든 계획과 완료 기준도 바꿔야 합니다. 중단 동의를 계속 요청하는 대신 서비스 제어 경로를 제거하고 Dovecot, SQLite, Redis의 온라인 수집으로 나눴습니다. 실제 운영 메일을 중단하는 방식은 실행하지 않았습니다. 요구가 바뀌면 카드와 설명서, 시험도 함께 고쳐야 한다는 점을 보여 주는 사례입니다.

## 15. 중단 없는 수집의 한계도 남깁니다 · 11:15 · 55초

중단 없이 수집했다고 해서 모든 자료가 완전히 같은 순간의 상태가 되는 것은 아닙니다. 우편함은 사용자별로 복사하고 SQLite와 Redis도 각각 전용 절차를 사용합니다. SMTP 대기열은 검사 시점에 비어 있어야 하며 메일이 관측되면 기존 서비스를 유지하고 백업을 실패로 남깁니다. 전체 공통 시점이나 모든 송수신 상태를 보장했다고 쓰지 않았습니다. 제한을 결과와 함께 적는 것이 복구 계획에 도움이 됩니다.

## 16. 합성 시험과 실제 복구 증거를 구분합니다 · 12:10 · 55초

숫자가 서로 다른 의미를 갖는다는 점을 강조하고 싶습니다. 123개는 합성 자료로 확인한 자동 시험의 개수입니다. 실제 공유기에 저장한 백업에서는 설정 파일과 메일 SQLite, 일곱 우편함의 읽기를 확인했습니다. 별도 PostgreSQL에서는 다섯 데이터베이스를 복원하고 읽었습니다. 이 결과를 전체 메일 서비스 로그인이나 애플리케이션 기능 검증으로 확대하지 않았습니다. 시험 이름보다 실제로 어디까지 실행했는지가 중요합니다.

## 17. 복원해 보고 용량도 측정했습니다 · 13:05 · 60초

첫 성공본의 암호화 크기는 약 2.819GiB였습니다. 같은 크기 다섯 개는 약 14.094GiB이고 새 성공본을 확인한 뒤 지우기 위해 잠시 여섯 개를 두면 약 16.912GiB입니다. 사용자가 정한 50GiB 범위 안이라는 현재 크기의 추정입니다. 앞으로의 증가나 실패 조각, 임시 공간까지 무한히 충분하다는 뜻은 아닙니다. 운영 데이터베이스의 원래 행 수 기준은 없었으므로 원본과 행 수가 같다고도 주장하지 않았습니다.

## 18. 서버 밖의 키로 실제 백업을 열었습니다 · 14:05 · 50초

서버가 고장 났는데 키도 그 서버에만 있으면 암호화 백업을 열지 못할 수 있습니다. 운영자가 외부에 기존 키를 보관하고 다시 꺼내 숨김 입력했습니다. 도구는 그 키로 실제 공유기 백업 명세를 복호화했습니다. 방송에서는 키를 확인하거나 입력하는 장면을 찍지 않습니다. 에이전트가 외부 암호 관리자 자체를 검사한 것은 아니고 운영자 확인과 실제 재입력 결과를 기록한 것입니다.

## 19. 스냅샷이 오류 재현 자료가 됐습니다 · 14:55 · 60초

자동 실행을 설치할 때 또 다른 오류가 나왔습니다. 처음 연결할 때 만든 설정에는 나중에 추가한 형식 항목이 없었고, 백업기는 기본값을 적용했지만 설치기는 이를 누락 오류로 처리했습니다. 보존한 열 번째 단계의 설정 예제로 같은 거부를 재현했습니다. 설치기도 같은 기본값을 사용하도록 고쳤고 실제 재적용이 통과했습니다. 중간 스냅샷이 영상 장면뿐 아니라 이전 상태를 재현하는 근거가 된 장면입니다.

## 20. 사용자 의견: 승인 입력이 너무 길었습니다 · 15:55 · 45초

설치가 성공한 뒤 사용자가 승인 문구가 너무 길다고 말했습니다. 앞으로는 계획을 읽은 뒤 y 한 글자로 승인하고 Enter는 취소하도록 바꿨습니다. 여기서 중요한 점은 이미 저장한 정책의 기준 문장까지 바꾸지 않았다는 것입니다. 그 값을 바꾸면 매일 실행기가 기존 승인을 거부할 수 있었습니다. 입력만 짧게 바꾸고 이전 승인 기록이 그대로 유효한지 시험했습니다. 이미 설치한 사용자에게 다시 입력을 요구하지 않았습니다.

## 21. 일일 예약 활성과 첫 실행 성공은 다릅니다 · 16:40 · 50초

이 화면은 일일 예약과 공유 연결 설정이 실제로 활성화된 시점의 공개 진행 카드입니다. 다음 예약은 사례 당시 한국 시간10월21일 오전4시였습니다. timer가 켜져 있다는 사실과 그 예약이 실제 성공했다는 사실은 다릅니다. 자료 제작 기준으로 첫 예약 성공과 재부팅 연결, 메일 전체 서비스 복구는 남아 있습니다. 서버의 기본 Result 성공 표시를 실행 증거로 오해하지 않도록 실제 시작 시각도 확인했습니다.

## 22. 시연 1 · 공개 저장소와 대본을 엽니다 · 17:30 · 90초

첫 시연은 공개 자료만 사용합니다. 공개 저장소의 README에서 원본 dev-process-light 링크와 이번 사례의 작업 흐름을 보여 줍니다. 이어서 이 강의의 HTML 파일을 열고 P를 눌러 발표 모드, N을 눌러 대본을 보여 줍니다. 단계 스냅샷은 당시 만든 진행 카드라는 점을 설명합니다. 원본 운영 프로젝트의 조사 문서나 보호된 터미널로 전환하지 않습니다. 실제 화면 전환 순서는 별도 시연 대본에 준비해 두었습니다.

## 23. 시연 2 · 합성 자료 시험을 실행합니다 · 19:00 · 90초

두 번째 시연은 공개 체크아웃의 합성 자료 시험입니다. 관리자 권한 없이 표시된 명령을 실행합니다. 결과가 내려가는 동안 손상 파일, 잘못된 경로, 빈 승인 입력처럼 실패해야 하는 경우도 시험한다는 점을 설명합니다. 처음 녹화할 환경에서는 Python과 GnuPG가 준비됐는지 미리 확인합니다. 시간이 부족하면 동봉한 공개 시험 결과를 열어 볼 수 있지만 방금 실행한 것처럼 소개하지 않습니다. 운영 백업이나 실제 키 확인 명령은 시연하지 않습니다.

## 24. 여러분의 작은 작업에도 적용해 보세요 · 20:30 · 50초

백업 도구 전체를 그대로 도입할 필요는 없습니다. 먼저 원본 dev-process-light 저장소에서 설치 안내를 읽고 작은 작업 하나에 적용해 보세요. 완료 기준을 세 가지 정도로 적고, 합성 자료로 성공과 실패를 확인한 뒤, 설명서와 기록을 같은 Git 저장에 넣어 봅니다. 이 사례의 공개 코드는 특정 서버 구성을 일반 예시 이름으로 바꾼 학습 자료입니다. 실제 설치에는 자신의 경로와 서비스 구성을 확인하고 별도 검증해야 합니다.

## 25. 기록은 다음 복구와 다음 개발을 돕습니다 · 21:20 · 35초

오늘 사례의 핵심은 요구가 코드로 이어지고 실행 증거가 다시 다음 작업으로 이어졌다는 점입니다. 기록은 영상을 만들 때도 도움이 됐지만 복구를 준비하고 오류를 재현할 때 더 직접적으로 쓰였습니다. 원본 dev-process-light와 smb-backup-lab 링크는 화면과 설명란에 넣었습니다. 확인하지 않은 부분은 계속 남은 시험으로 표시하겠습니다. 여러분의 작은 프로젝트에서도 이 흐름을 한 번 적용해 보시면 좋겠습니다.

## 26. 부록 · 자주 받는 질문 · 21:55 · 0초

질의응답에서 자주 나올 수 있는 범위를 정리했습니다. 현재 대상은 SMB 공유이며 다른 저장소 지원을 구현했다고 소개하지 않습니다. 서버 전체를 부팅 가능하게 복제하는 백업도 아닙니다. 메일은 확인한 SQLite와 우편함 읽기, 남은 전체 서비스 검증을 구분합니다. 실패한 날에는 새 성공본 검증이 없으므로 기존 성공본 보관 정리가 진행되지 않습니다. 이 페이지는 본편 시간에서 제외한 선택 부록입니다.
