# light-save — 저장하기

## 언제 -- 단계마다 자주
| 단계가 끝남 | 저장 종류 | 예 |
|---|---|---|
| 작업 카드 합의 (`light-start`) | `중간 저장:` | `중간 저장: 할 일 목록 - 작업 카드 합의` |
| 만들기 한 덩어리 (30분 안쪽, 확인 전) | `중간 저장:` | `중간 저장: 할 일 목록 - 입력 칸까지` |
| 확인 끝 (`light-check`, 사용자 확인) | `기능:` `수정:` `모양:` `정리:` | `기능: 할 일 목록 - 입력과 목록` |
| 데이터 설계·변경 확인받음 (`data-light`, verify 통과) | `데이터:` | `데이터: 회원·회비 표 설계` |
| 되돌림 (`light-undo`) | `되돌리기:` | |
| 하루 작업을 마칠 때 | `중간 저장:` | |

자주 저장할수록 되돌아올 수 있는 지점이 많아진다. 확인하지 않은 것은 `중간 저장:` 으로만 저장한다.

## 순서
1. `git status` 로 바뀐 파일을 본다. **이번 작업과 상관없는 파일**이 있으면 사용자에게 묻는다
   ("이 파일도 같이 저장할까요?"). 비밀번호·키가 든 파일(`.env` 등)은 저장하지 않는다.
   실제 데이터(`data/app.db`, `data/backup/`)·가져온 원본 엑셀·CSV·가져오기 계획(`import_plan*.json` -- 실제 값이 들어 있다)도 저장하지 않는다 --
   목록에 보이면 `.gitignore` 부터 고친다 (`light-start` 의 "넘겨주는 순서" 5번에 있는 데이터 줄).
2. 설명서: 카드의 `설명서:` 가 해당 없음이 아니면 `manual/` 이 이번 변경과 맞게 고쳐졌는지 본다.
   안 고쳐졌으면 저장하기 전에 `light-manual` 로 고친다. "해당 없음"이면 이유가 카드에 있는지 본다.
3. 기록을 고친다 (커밋에 같이 들어가게 **저장 전에**):
   - `FEATURES.md`: 새 기능 줄 추가 또는 상태·파일·확인 방법·설명서 갱신
   - `NOW.md`: "지금 작업" 을 비우거나 다음 단계 카드로 바꾸고, "다음에 할 일" 과 "마지막 저장" 을 고친다
   - `DECISIONS.md`: 이번에 중요한 결정을 했으면 한 줄 (예: "데이터는 브라우저에만 저장 -- 서버 없이 쓰려고")
   - `NAMES.md`: 새 이름을 썼으면 추가 (데이터의 표·칸 이름은 정본에 있으니 옮겨 적지 않는다)
   - 데이터를 바꿨으면: `FEATURES.md` 의 "데이터 (표)" 절(표 → 쓰는 기능), `NOW.md` 의 "저장하는 데이터"·"개인정보"
   - 작업 기록 세 층 (아래 "기록하는 법") -- 비밀번호·키·개인정보는 적지 않는다.
4. 저장한다 (설명서도 같은 저장에):
   ```
   git add <이번 작업 파일들> dev-notes/ manual/        ← 있는 것만 (없는 폴더를 주면 git add 가 아무것도 넣지 않고 실패한다)
   git commit -m "기능: 할 일 목록 - 입력과 목록"
   ```
   데이터 설계를 고쳤으면 정본과 생성물도 같은 저장에: `git add data/model.light.json data/out/` (가져오기를 했으면 `data/import_log.jsonl` 도 --
   행의 값은 없고 언제·몇 행·사용자 승인 답이 있는 기록이다. Supabase 규칙 틀을 손으로 실행했으면 `data/supabase-policies.sql`. 데이터 검사 장치를 처음
   설치했으면 `.data-light/`·`.gitignore` 와, 만들어졌으면 `.github/workflows/data-light.yml`).
   **데이터 검사 장치가 저장을 멈추면** `--no-verify` 로 건너뛰지 않는다 -- 나온 FAIL 줄이 문제다. `light-check` 의 "문제가 나면" 으로 간다.
   "python 을 찾지 못해 검사를 건너뜁니다" 가 나오면 저장은 됐지만 검사는 안 된 것이다 -- 사용자에게 알리고 파이썬을 찾을 때까지 `light-check` 로 직접 `verify`.
   메시지는 한국어로 짧게, 앞에 종류를 붙인다: `기능:` 새 기능 · `수정:` 고침 · `모양:` 디자인 · `정리:` 기타 · `데이터:` 데이터 설계·변경(data-light) · `중간 저장:` 미완성 · `되돌리기:` 되돌림(light-undo)
5. 인터넷 저장소에 올리기 -- `NOW.md` `## 설정` 의 `인터넷 저장소에 올리기(push):` 를 따른다.
   - `예` → `git push`. 실패하면 이유를 말하고(인터넷·로그인 등) 저장은 내 컴퓨터에 그대로 있다고 알린다.
   - `아니오` → 올리지 않는다.
   - `(아직 정하지 않음)` 이고 `git remote` 에 저장소가 있으면 **한 번만** 묻는다:
     "저장할 때마다 인터넷 저장소(<주소>)에도 올릴까요? 다른 컴퓨터에서도 이어서 할 수 있고, 저장소가 공개면 누구나 볼 수 있어요."
     답을 `## 설정` 과 `DECISIONS.md`(`[사용자]`, 답 그대로)에 적는다. 저장소가 없으면 묻지 않는다.
   - 올리기로 정했는데 데이터 검사 장치를 GitHub 검사 파일 없이(`--no-ci`) 깔았으면 "인터넷 저장소에서도 데이터 설계를 검사할까요?" 를 한 번 묻고,
     예면 `datalight.py hook install --ci` (`.github/workflows/data-light.yml` 이 생긴다 -- 다음 저장에 넣는다).
6. 기록 보기 페이지 -- `## 설정` 의 `기록 보기 페이지:` 가 경로면 `light-portal` 로 다시 만든다 (만들지 않음이면 건너뜀).
   도구가 `.gitignore` 에 줄을 더했다고 알리면(처음 만들 때) 그 `.gitignore` 를 바로 `정리: 기록 보기 페이지는 저장하지 않음` 으로 저장한다.
7. 사용자에게 한 줄로 알린다: "저장했습니다: 기능: 할 일 목록 - 입력과 목록 (되돌아올 수 있는 지점)" + 올렸으면 "· 인터넷 저장소에도 올림"
8. 설명서를 만들거나 고쳤으면 바로 이어서 **채팅에 그대로 보여 준다** (`light-manual` 의 "저장 후 채팅에 보여 주기").

## 기록하는 법 (세 층)
기록은 많아진다. 나중에 AI 가 전부 읽지 않아도 되게 **흐름 → 목록 → 자세히** 세 층으로, **기능·날짜별**로 나눈다.

| 층 | 어디에 | 무엇을 |
|---|---|---|
| ① 흐름 | `dev-notes/LOG.md` 맨 위(설명 아래) | `- 2026-10-11 14:40 · 만들기 · 할 일 · 입력과 목록 · 중간 저장 · AI` -- 단계·기능·한 줄 |
| ② 목록 | `dev-notes/log/<기능>/<날짜>.md` 의 `## 목록` | 한 일을 한 줄씩, 번호를 붙여: `- #2 14:40 [만들기] todo.js·index.html (TodoList)` |
| ③ 자세히 | 같은 파일 `## 자세히` 의 `### #번호` | 아래 표의 내용 |

- `<기능>` 은 `FEATURES.md` 의 기능 이름 그대로 (폴더 이름은 빈칸만 `-` 로: `할 일` → `dev-notes/log/할-일/`). 흐름 줄의 기능 칸도 같은 이름.
  여러 기능에 걸친 일은 `전체`. 데이터 설계·변경(`data-light`)은 `데이터` (`dev-notes/log/데이터/`) -- 표의 역사를 한곳에서 본다.
- 단계별로 남기는 것:

| 단계 | ② 목록에 | ③ 자세히에 |
|---|---|---|
| 기획 (작업 카드 합의) | 카드 제목 | 목표·완료 기준·건드릴 기능·사용자 답 |
| 만들기 | 고친 파일·클래스 | 파일마다 경로·클래스·함수(메소드)·변수 -- 추가/수정/삭제 |
| 확인 | 확인한 것(완료 기준·다른 기능) | 한 일 · 결과(통과·실패·확인 못 함) · 오류 메시지(앞부분) · 해결 방법 |
| 운영 (사이트를 공개한 뒤 점검·고침) | 한 운영 작업 | 관련 기획 · 관련 파일 · 한 일 · 결과 · 오류 |
| 평가 (써 보고 돌아보기) | 평가한 기능 | 좋았던 점·불편한 점·다음에 고칠 것 (평가 보고서) |
| 데이터 (`data-light` 설계·변경·DB 만들기·가져오기) | 표 설계·변경 한 줄 | 더하고 바꾸고 뺀 표·칸 · 성공 기준·만들지 않을 것 · 사용자 답 · DB 종류와 이유 · verify 결과 · DB 를 만들었거나 데이터를 넣었으면 언제·어디에·몇 행·사용자 승인 답 |

예 -- `dev-notes/log/할-일/2026-10-11.md`:
```
# 할 일 -- 2026-10-11

## 목록
- #1 14:25 [기획] 할 일 목록 카드 합의
- #2 14:40 [만들기] todo.js·index.html (TodoList)
- #3 15:02 [확인] 새로고침해도 남는지 -- 실패

## 자세히
### #2 14:40 [만들기]
- `todo.js`: 함수 `addTodo` 추가, `render` 수정, 변수 `todos` 추가
- `index.html`: 메뉴 한 줄 추가
### #3 15:02 [확인]
- 한 일: 할 일 2개 적고 새로고침
- 결과: 실패 -- 목록이 비어 있음
- 오류: (콘솔) `SyntaxError: Unexpected token u in JSON`
- 해결: 저장 이름이 달랐음 (todo → todos), 고친 뒤 다시 확인해 통과
```

## 하지 않는 것
- 확인(light-check) 없이 "기능:" 으로 저장하기 -- 미완성이면 "중간 저장:" 으로 한다
- 새 기능·사용법 변경인데 설명서 없이 "기능:" 으로 저장하기
- 인터넷 저장소에 올리기(push)를 한 번도 묻지 않고 하기, 배포(사이트 공개)를 묻지 않고 하기
- 작업 기록(LOG.md) 없이 저장하기
- `git add -A` 로 무엇이 들어가는지 모른 채 저장하기
