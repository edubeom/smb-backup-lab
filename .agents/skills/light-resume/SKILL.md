# light-resume — 이어하기

## 언제
- 새 대화·새 세션을 시작할 때 (사용자가 아무 말 없이 기능을 요청해도 먼저 한다)
- 사용자가 "어디까지 했지?", "이어서 하자"라고 할 때

## 순서
1. 읽는다: `dev-notes/NOW.md`, `dev-notes/FEATURES.md`, `dev-notes/NAMES.md`, `dev-notes/LOG.md` 의 맨 위 5줄
   (`LOG.md` 가 없으면 설치본의 형식대로 만든다 -- 예전 버전에서 올라온 프로젝트).
   `dev-notes/log/` 의 기능별 파일은 지금 필요한 기능·날짜 것만 연다 -- 전부 읽지 않는다.
   `data/model.light.json`(데이터 설계 정본)이 있으면 표 이름·이름표만 훑는다 (자세한 것은 그 일을 할 때 `data/out/spec.md`).
2. 확인한다:
   - `git status` -- 저장하지 않은 변경이 있는가
   - `git log --oneline -5` -- 최근 저장 5개
3. 사용자에게 5줄 이내로 말한다 (데이터 설계가 있으면 한 줄 더):
   ```
   지금 상황: <이 프로젝트 한 줄>
   마지막 저장: <날짜·내용>
   진행 중이던 작업: <NOW.md 의 지금 작업, 없으면 "없음">
   저장 안 된 변경: <있음(파일 몇 개) / 없음>
   다음 할 일: <NOW.md 의 다음에 할 일 첫 줄>
   데이터: <표 4개 (회원·회비…) · Supabase -- 정본 data/model.light.json>   ← 정본이 있을 때만
   ```
4. 저장 안 된 변경이 있으면: 무엇인지 보여주고 "이어서 마저 할지 / 되돌릴지(light-undo)"를 묻는다. 마음대로 지우지 않는다.
   (바뀐 것이 설치로 생긴 파일뿐이면 묻지 않고 아래 "다시 설치한 뒤" 로)
5. 짝 스킬 확인: `data/model.light.json` 이 있는데 `.claude/skills/data-light`(Codex 는 `.agents/skills/data-light`)가 없으면
   "데이터 설계 스킬(data-light)이 설치되어 있지 않아요. dev-process-light 를 다시 설치하면 같이 깔려요 (기록은 그대로)" 라고 알린다.
   `## 설정` 의 데이터 검사 장치가 `설치함` 인데 `datalight.py hook status` 가 `훅: 없음` 이면(다른 컴퓨터에서 받은 저장소 -- 훅은 저장되지 않는다)
   "이 컴퓨터에는 데이터 검사 장치가 없어요. 다시 설치할까요?" 라고 **한 번** 묻는다 (`datalight.py hook install`).
   아니오면 `## 설정` 을 `다른 컴퓨터에만` 으로 고쳐 다음부터 묻지 않는다 (`설치함` 일 때만 확인·다시 설치를 한다).
6. 예전 버전에서 올라온 프로젝트면 빠진 칸을 채운다 (내용은 지어내지 않는다): `NOW.md` "이 프로젝트는" 아래의 다섯 줄
   (누가 쓰나·로그인·올리는 곳·저장하는 데이터·개인정보 -- 기록에서 알 수 있는 것만, 나머지는 `(아직 모름)`),
   데이터 정본이 있으면 `FEATURES.md` 의 "데이터 (표)" 절(`| 표 | 이름표 | 쓰는 기능 |`), `## 설정` 에 `- 데이터 검사 장치: (아직 정하지 않음)` 줄
   (`datalight.py hook status` 가 `훅: 없음` 이 아니면 `설치함`). 다섯 줄의 형식:
   ```
   - 누가 쓰나: 나 혼자
   - 로그인: 없음
   - 올리는 곳: 정적 호스팅(GitHub Pages)
   - 저장하는 데이터: 브라우저에만        (없음 / 브라우저에만 / data-light 설계 · 실제 저장은 <브라우저·SQLite·Supabase> / 다른 곳)
   - 개인정보: 없음
   ```

## 다시 설치한 뒤 (새 버전으로 올렸을 때)
`git status` 의 바뀐 파일이 저장해 둔 `.claude/skills/`·`.agents/skills/`·`AGENTS.md`(규칙 블록)·`.data-light/datalight.py` 의
**고침**(` M`)과 그 폴더 안의 새 파일뿐이면 사용자가 dev-process-light 를 새로 설치한 것이다 (스킬 폴더를 한 번도 저장하지 않아 `??` 로만 보이면
아니다 -- 첫 저장 때 같이 넣지 않은 것이니 다음 저장에 넣는다). "이어서 할지 / 되돌릴지" 묻지 않고 이렇게 한다:
1. 사용자에게 한 줄로 알린다: "dev-process-light 를 새 버전으로 설치하셨네요. 맞춰 두고 저장할게요."
2. 데이터 검사 장치가 `설치함` 이면 `datalight.py hook status` 를 보고 (`python .claude/skills/data-light/scripts/datalight.py`):
   - `결과: 최신` → 그대로.
   - `결과: 버전이 다릅니다` 또는 `훅: 없음` → `datalight.py hook install`. 이때 `.github/workflows/data-light.yml` 이 없으면 `--no-ci` 를 붙인다
     (예전 버전은 늘 만들었으니, 없다면 사용자가 지운 것이다 -- 되살리지 않는다).
     결과에 "이미 있어 건드리지 않았습니다" 가 나오면(`git config core.hooksPath` 가 있는 저장소 등 -- 예전 버전은 `.git/hooks` 에만 깔았다)
     다른 검사 훅이 그 자리에 있는 것이다 -- 사용자에게 알리고, 좋다고 하면 `--append`. 다시 `hook status` 로 `결과: 최신` 을 확인한다
     (`hook install` 이 이 컴퓨터의 sh 가 훅을 읽는지 스스로 확인한다 -- 못 읽는다고 나오면 `light-start` "넘겨주는 순서" 5 대로).
   - `안 함 (이 컴퓨터의 sh 가 훅을 못 읽음 …)` 이면 다시 설치할지 묻는다 (data-light 0.4.1 부터 macOS 의 sh 도 읽는다).
3. `data/model.light.json` 이 있으면 장치 결과와 상관없이 늘 `build`(정본의 `db` 대로) → `verify`.
   `verify` 가 **유형 미정**(정본에 `product` 가 없음 -- data-light 0.5.0 부터 필수)으로 실패하면 `light-start` "넘겨주는 순서" 4 의 만드는 것을 따른다:
   처음 답·`NOW.md`·`DECISIONS.md` 에 사용자가 말한 "무엇을 만드나"가 있으면 그 말 그대로 `said` 로 옮기고, 없으면 한 번 묻는다
   ("무엇을 만들어 드리는 건가요? 설계까지 / 파일 넣기 / 데이터 관리 / 분석"). 정본을 고친 것이니 `데이터:` 로 저장한다. 새 도구는 생성물을 다르게 만들 수 있다 --
   **다시 만들기 전에는 `verify` 가 "data/out 의 … 가 정본과 다릅니다" 로 실패하고, GitHub 검사 파일이 있는 저장소는 올렸을 때 GitHub 검사도 실패한다.**
   `git diff data/out` 으로 무엇이 바뀌었는지 쉬운 말로 알린다 (예: "Supabase 용 SQL 에 모든 표의 행 접근 규칙이 들어갔어요").
   이미 만든 DB(Supabase·`data/app.db`)에도 적용해야 하는 변경이면 **따로 묻고** 답을 받은 뒤에 바뀐 부분만 적용한다 (`light-start` 의 "넘겨주는 순서" 6).
   예전 버전의 한계 때문에 남긴 결정이 `DECISIONS.md` 에 있으면(예: "화면에서 막는다 -- 정본에 쓸 수 없어서", Supabase 규칙 틀을 손으로 골라
   `data/supabase-policies.sql` 로 실행함 → 지금은 정본의 `unique` 묶음·`signup`·`access`·`owner` 로 적을 수 있다), 새 버전으로 정본에 옮기는
   `데이터: 표 바꿈` 카드를 사용자에게 제안한다 (혼자 바꾸지 않는다). Supabase 규칙을 옮길 때: 손으로 고른 틀의 규칙 이름은 `build` 가 만드는
   이름과 같아 대개 다시 실행할 것이 없다 (`schema.sql` 과 실제 DB 를 비교해 보여 준다). 손으로 더한 `owner_id` 칸이 비어도 되는 칸이면
   비지 않게 바꿀지 따로 묻는다. 정본으로 옮긴 규칙은 `data/supabase-policies.sql` 에서 빼고, 정본으로 못 옮긴 것(읽기 규칙 등)만 남긴다.
4. 위 "예전 버전에서 올라온 프로젝트" 의 빠진 칸을 채운다.
5. 저장: `정리: dev-process-light 새로 설치 (스킬·규칙 갱신)` -- 흐름 `· 준비 · 전체 · 새 버전 설치 · 완료 · AI`.

## 처음 쓰는 프로젝트일 때
`dev-notes/` 가 없거나 `NOW.md` 의 "이 프로젝트는" 바로 아래 첫 줄이 안내문 `(무엇을 만드는지 …)` 그대로면:
1. `git status` 가 실패하면(아직 git 이 아니면) 사용자에게 알리고 `git init` 한다.
   `.gitignore` 가 없으면 만든다 (비밀 설정 파일·`node_modules/`·`.env` 등).
2. 사용자에게 묻는다: "무엇을 만드는 사이트인가요? 들어갈 기능을 생각나는 대로 말해 주세요."
3. 답을 `NOW.md` 의 "이 프로젝트는" 과 "다음에 할 일" 에 적고, 이미 있는 파일이 있으면 살펴서
   `FEATURES.md` 에 기능별로 정리한다 (모르는 것은 "확인 필요"로 적는다).
   답에서 알 수 있는 것은 "이 프로젝트는" 아래 다섯 줄(누가 쓰나·로그인·올리는 곳·저장하는 데이터·개인정보)에 적는다.
   모르는 것은 `(아직 모름)` 그대로 두고 **따로 묻지 않는다** -- 필요해질 때 그 일을 하는 스킬(`light-start`, `data-light`)이 한 번 묻는다.
   이미 `data/model.light.json` 이 있으면 저장하는 데이터를 `data-light 설계` 로 적고 `FEATURES.md` 의 "데이터 (표)" 절을 채운다.
4. 준비 질문 (기획 질문과 별개, 짧게):
   - 기록 보기 페이지를 만들지와 위치 -- `light-portal` 의 질문 그대로 (잘 모르면 1번 추천)
   - `git remote` 에 인터넷 저장소가 있을 때만: 저장할 때마다 올릴지 (`light-save` 5번의 질문)
   답을 `NOW.md` `## 설정` 과 `DECISIONS.md`(`[사용자]`, 답 그대로)에 적는다. `NOW.md` 에 `## 설정` 이 없으면(예전 버전) 추가한다.
5. `LOG.md` 에 `· 준비 · 전체 · 작업 기록 시작 · 완료 · AI` 한 줄. 기록 보기 페이지를 만들기로 했으면 **첫 저장 전에** 한 번 만든다
   (`light-portal` -- 도구가 `.gitignore` 에 넣는 줄이 첫 저장에 같이 들어가게). 첫 저장(`light-save`): "준비: 작업 기록 시작" --
   설치된 스킬(`.claude/skills/`, `.agents/skills/`)·`AGENTS.md`·`CLAUDE.md`·`dev-notes/` 를 함께 넣는다 (다음에 다시 설치하면 무엇이 바뀌었는지 보인다).
   `DECISIONS.md` 의 `YYYY-MM-DD` 보기 줄은 첫 결정을 적을 때 지운다.

## 하지 않는 것
- 기록을 읽지 않고 바로 코드를 고치기
- NOW.md 에 없는 내용을 지어내기 (모르면 "기록 없음"이라고 말한다)
