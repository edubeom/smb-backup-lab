# light-start — 시작하기 전에 합의

## 언제
- "○○ 기능 만들어 줘", "○○ 바꿔 줘" 같은 요청을 받았을 때 -- **코드를 쓰기 전에**
- 오타·문구·색 하나 바꾸기처럼 아주 작은 일은 생략하고 바로 해도 된다 (그래도 끝나면 light-check)

## 순서
1. `dev-notes/FEATURES.md` 를 본다. 이번 요청이
   - 새 기능인지, 기존 기능을 바꾸는지
   - 어떤 파일을 건드릴지, 그 파일을 **다른 기능도 쓰는지** ("함께 쓰는 파일" 포함)
   - 저장하는 데이터가 생기거나 바뀌는지 (`NOW.md` 의 "저장하는 데이터", `FEATURES.md` 의 "데이터 (표)" 절)
   를 확인한다.
2. 요청이 크면 나눈다. 기준: **한 단계 = 30분 안에 만들고 확인할 수 있는 크기**, 단계마다 저장한다.
   예) "가계부" → ① 입력과 목록 ② 월별 합계 ③ 그래프
3. 작업 카드를 만들어 `dev-notes/NOW.md` 의 "지금 작업" 에 적고, 사용자에게 보여준다:
   ```
   ### 작업: 할 일 목록 (1/3 입력과 목록)
   - 목표: 할 일을 적고 체크할 수 있다
   - 완료 기준:
     - [ ] 할 일을 입력하고 Enter 를 누르면 목록에 추가된다
     - [ ] 체크하면 줄이 그어진다
     - [ ] 새로고침해도 목록이 남아 있다
   - 건드릴 기능: 할 일 (새 기능) -- 새 파일 todo.js, index.html 에 메뉴 1줄 추가
   - 영향 받을 수 있는 기능: 메모 (index.html 을 같이 씀) -- 끝나고 메모도 점검
   - 설명서: 장 추가 (manual/todo.html)
   - 데이터: 브라우저에만 (저장 이름 todos -- NAMES.md 에 적음)
   - 진행: 계획
   ```
   완료 기준은 **사람이 화면에서 직접 확인할 수 있는 문장**으로 쓴다 ("코드가 깔끔하다" 같은 것은 안 된다).
   `설명서:` 는 새로 만듦(처음) / 장 추가(새 기능) / 고침(사용 방법이 바뀜) / 해당 없음(이유) 중 하나 (`light-manual`).
   `데이터:` 는 없음 / 브라우저에만 / 새 표 / 표 바꿈 / 읽기만 중 하나 (아래 "저장할 데이터가 생기면").
4. "이대로 진행할까요?" 라고 묻고, 사용자가 고치면 카드를 고친다. **확인받기 전에는 만들지 않는다.**
5. 새 이름이 필요하면 `dev-notes/NAMES.md` 를 보고, 없으면 카드와 함께 제안한다.
6. 확인받으면 진행을 "만드는 중" 으로 바꾸고 기록한다:
   - 사용자가 정한 것(무엇을 넣고 뺄지 등)은 `DECISIONS.md` 에 `[사용자]` 로 **사용자의 말 그대로**.
   - AI 가 정한 기술 선택(어떤 방식으로 저장할지, 어떤 라이브러리를 쓸지 등)은 `[AI]` 로 이유와 다른 안을 함께,
     그리고 사용자에게 한두 줄 쉬운 말로 알려 준다 ("이번엔 브라우저에 저장하는 방식으로 할게요 -- 서버가 필요 없어서요").
   - 기록 세 층(`light-save` 의 "기록하는 법"): 흐름 `· 기획 · <기능> · <작업 제목> 카드 · 확인받음 · 사용자`,
     그 기능·날짜 파일에 목록 한 줄과 자세히(목표·완료 기준·사용자 답). 그리고 `light-save` 로 `중간 저장:` 한다.

## 만드는 동안
- 카드에 적은 파일만 고친다. 다른 기능의 파일을 고쳐야 할 것 같으면 **멈추고 먼저 말한다.**
- 사용자가 중간에 요청을 바꾸면 카드를 먼저 고치고 다시 확인받는다.
- 한 덩어리를 만들 때마다(30분 안쪽) 기록(흐름 `· 만들기 ·` 한 줄 + 목록 + 자세히: 고친 파일·클래스·함수·변수)을 남기고 `중간 저장:` 한다.
- 다 만들면 `light-check` 로 간다. "다 됐습니다" 라고 먼저 말하지 않는다.

## 저장할 데이터가 생기면 -- 짝 스킬 `data-light` 로 넘겨주기
`data-light`(data-expert-framework-light)는 이 규칙과 짝인 데이터 설계 스킬이다. 같이 설치되어 있다 (`.claude/skills/data-light`).
아래의 `datalight.py` 는 `python .claude/skills/data-light/scripts/datalight.py` (Codex 는 `.agents/skills/...`) -- `.data-light/datalight.py` 는
데이터 검사 장치가 커밋할 때 쓰는 사본이라 직접 부르지 않는다.
카드의 `데이터:` 는 아래 중 하나다.

| 데이터 | 언제 | 하는 일 |
|---|---|---|
| 없음 | 저장하는 것이 없다 (화면·글·모양만) | -- |
| 브라우저에만 | 이 기기 브라우저에 간단한 목록 하나 (메모·할 일 정도) | 저장 이름을 `NAMES.md` 에 적는다. 이름·모양을 바꾸면 쓰던 데이터가 안 보일 수 있다고 카드에 적고 먼저 말한다 |
| 새 표 | 아래 "넘겨줄 때" 에 하나라도 해당 | **이 일의 첫 단계가 데이터 설계** -- `data-light` 로 정본을 만들고 확인받은 뒤에 화면을 만든다 |
| 표 바꿈 | 이미 있는 표·칸을 더하거나 바꾸거나 뺀다 | 정본부터 고친다. `FEATURES.md` 데이터 절에서 그 표를 쓰는 기능을 찾아 "영향 받을 수 있는 기능"에 적는다. 데이터가 든 표·칸을 빼거나 이름을 바꾸면 그 데이터가 사라질 수 있다고 먼저 말한다 |
| 읽기만 | 있는 표를 보여 주기만 | 정본의 표·칸 이름을 그대로 쓴다 |

넘겨줄 때 -- 하나라도 해당하면 `data-light`:
- 표가 둘 이상이고 서로 이어진다 (손님 → 주문, 회원 → 회비)
- 여러 기기·여러 사람이 같은 데이터를 본다 (로그인, 서버, Supabase)
- 엑셀·CSV 를 넣는다
- 개인정보(이름·연락처·주소 등)를 저장한다
- 브라우저에만 두던 데이터가 위에 해당하게 자랐다 (옮길 때 쓰던 데이터를 어떻게 할지 먼저 묻는다)

넘겨주는 순서:
1. 큰 일을 나눌 때 데이터 설계를 **1단계**로 둔다. 예) "동아리 회비" → ① 데이터 설계 ② 회원 명단 ③ 회비 입력 ④ 미납 보기.
   데이터 설계 카드의 완료 기준은 "그림과 표를 보고 맞다고 했다", "`verify` 통과" 처럼 확인할 수 있는 문장으로.
2. `NOW.md` "이 프로젝트는" 의 답(누가 쓰나·로그인·올리는 곳·개인정보)을 그대로 쓴다 -- **이미 답한 것은 다시 묻지 않는다.**
   `(아직 모름)` 인 것만 한 번에 하나씩 쉽게 묻고, 답을 그 줄과 `DECISIONS.md`(`[사용자]`, 답 그대로)에 적는다:
   - 누가 쓰나요? -- 나 혼자 / 몇 명이 같이 (누구) / 아무나 가입해서
   - 로그인해서 쓰나요? -- 아니요 / 네 (각자 아이디로)
   - 어디에서 쓰나요? -- 내 컴퓨터에서만 / 인터넷에 올려서 (GitHub Pages 같은 무료 호스팅·Supabase 등) / 잘 모름 (AI 가 추천)
3. **실제로 어디에 저장할지** -- 답에 따라 AI 가 정하고 `NOW.md` "저장하는 데이터" 줄과 `DECISIONS.md`(`[AI]`, 이유·다른 안)에 적는다.
   설계(정본)는 어느 경우든 `data-light` 로 하고, 화면이 실제로 읽고 쓰는 곳만 다르다:

   | 답 | 화면이 읽고 쓰는 곳 | "저장하는 데이터" 줄 |
   |---|---|---|
   | 혼자 · 인터넷 정적 호스팅(GitHub Pages 등) | 그 기기의 브라우저 저장소 -- 정본의 표·칸 이름 그대로 (`data/app.db` 는 만들지 않는다 -- verify 는 메모리에서 시험한다) | `data-light 설계 · 실제 저장은 브라우저` |
   | 혼자 · 내 컴퓨터에서만 | SQLite `data/app.db` + 내 컴퓨터에서 도는 작은 서버(파이썬 등) | `data-light 설계 · SQLite (data/app.db)` |
   | 여럿이 · 로그인 | Supabase (PostgreSQL) -- 정본은 `"db": "postgresql"` + 누가 볼 수 있나(`signup`·`access`, 아래 4) | `data-light 설계 · Supabase` |
   | 여럿이 · 로그인 없음 | 로그인을 넣자고 권한다 -- 로그인 없이 여럿이 쓰는 저장소는 주소만 알면 누구나 읽고 바꿀 수 있다고 그대로 말하고, 사용자가 고르게 한다 | (사용자 답대로) |
   | 이미 쓰는 DB 가 있음 | 그 DB -- 아래 "이미 DB 가 있으면" | `data-light 설계 · <그 DB>` |

   브라우저 저장이면 DB 가 규칙(필수·선택값·가리킴·같은 값 금지·묶음 중복 금지)을 지켜 주지 않는다 -- 정본에 적은 규칙을 화면 코드가 지켜야 하므로
   그 기능 카드의 완료 기준에 넣는다 (예: "이름을 비우고 저장하면 막힌다", "같은 달 회비를 두 번 넣으면 막힌다").
   또 데이터는 **그 기기·그 브라우저에만** 있고 사이트 데이터를 지우면 사라진다 -- 백업(파일로 내보내기·불러오기)을 만든다고 알리고
   카드의 완료 기준에 넣는다 (사용자가 원하지 않으면 빼고 답을 `DECISIONS.md` 에).
4. `data-light` 의 흐름(이해 → 설계 → 확인)을 따른다. **이미 정한 것은 옮겨 적고 다시 묻지 않는다:**
   **만드는 것(`product`) 먼저** -- 사용자가 이미 말한 "무엇을 만드나"(처음 답, 카드)를 정본 `product` 로 옮긴다:
   `kinds` 는 설계까지(`design`) · 파일 넣기(`load`) · 데이터 관리(`manage`, 넣고 고치고 찾는 사이트) · 분석(`analyze`, 집계·보고) 중 맞는 것(여러 개 가능),
   `said` 는 **사용자 말 그대로**(짐작해 고쳐 쓰지 않는다). 둘 이상이면 무엇이 주 목적인지 한 번 묻고 `main` 과 그 답 그대로 `main_said`.
   말한 것이 없으면 "무엇을 만들어 드릴까요?" 를 한 번 묻는다. 없으면 `verify` 가 **유형 미정**으로 실패한다 (data-light 0.5.0).
   `analyze` 가 들어 있으면 성공 기준(`goals`)이 하나 이상 있어야 한다. 답은 `DECISIONS.md` 에 `[사용자]` 로.
   카드·`NOW.md` 다음에 할 일에 있는 "데이터로 알 수 있어야 하는 것"(예: 미납 보기 → "이번 달 회비를 안 낸 활동 회원을 볼 수 있다")은
   data-light 의 성공 기준(`goals`)으로, 사용자가 "이번엔 안 한다"고 한 것(카드·`DECISIONS.md`)은 만들지 않을 것(`not_doing`)으로.
   없는 것만 data-light 가 묻고, 답은 `DECISIONS.md`(`[사용자]`)에도 적는다.
   **샘플 행(`sample`)과 성공 기준의 기대 결과(`expect`)는 만든 값으로** 쓴다 -- 가져온 엑셀·CSV 의 실제 이름·연락처를 옮겨 적지 않는다 (정본은 저장되고 올라간다).
   두 칸을 묶어야 중복이 되는 것(한 회원은 한 달에 회비 한 번)은 표의 `"unique": [["member_id", "dues_month"]]` 로 정본에 적는다 --
   DB(SQLite·Supabase)가 막아 준다 (브라우저 저장이면 위처럼 화면 코드도 막는다).
   **Supabase 면 누가 볼 수 있는지도 정본에** -- "누가 쓰나" 답으로 AI 가 정하고 `DECISIONS.md` 에 `[AI]`(이유·다른 안)로 남긴다.
   `build` 가 이대로 실제 행 접근 규칙(RLS policy)을 만든다:

   | 누가 쓰나 | 정본 |
   |---|---|
   | 정해진 사람끼리 (임원 3명 등) | `"signup": "closed"` + 표마다 `"access": "members"` -- Supabase 에서 **새 가입을 꺼야** 한다 (켜 두면 아무나 가입해 다 읽는다. `closed` 가 없으면 `check` 가 막는다). 계정은 사용자가 Supabase 에서 만든다 (아래 6) |
   | 아무나 가입 | `"signup": "open"` + 자기 것만 보는 표에 owner 칸 `{"name": "owner_id", "label": "만든 사람", "type": "owner"}` 과 `"access": "own"` (`pi_` 표의 `own` 은 짝 표의 주인을 따른다) |
   | 누구나 보는 목록 | 그 표만 `"access": "read"` (읽기만, `pi_` 표에는 쓸 수 없다) |

   `split --write` 가 짝 표의 `access` 를 `pi_` 표로 옮겨 준다 (짝 표가 `read` 면 옮기지 않는다 -- 짝 표에 owner 칸이 있으면 `own`, 없으면 비워 두기:
   사이트에서는 못 읽고 Supabase 화면에서만). 나눈 뒤 `pi_` 표의 `access` 가 짝 표와 맞는지 본다 (`check` 가 빠졌으면 참고로 알린다).
   읽기와 쓰기가 다르면 `access` 를 **두 개 목록**으로 적는다: **"누구나 읽고, 쓰기는 자기 것만(게시판)"** = `["read", "own"]`,
   **"누구나 읽고, 쓰기는 임원만(공지)"** = `["read", "members"]` -- `build` 가 읽기·쓰기 규칙을 따로 만든다 (손으로 쓰는 읽기 규칙이 필요 없다).
   `read` 만 준 표는 사이트에서 쓸 수 없다 -- 내용은 사용자가 Supabase 의 Table Editor 에서 넣는다.

   **하는 일(`works`)** 3~7개는 사용자에게 묻지 않고 1·2번 답과 `FEATURES.md` 에서 정리한다 (일 · 누가 · 화면 · 쓰는 표와 C·R·U·D) --
   `build` 가 만드는 **데이터 설명서**(`data/out/book.html`: 하는 일 → 화면 → 표 → 예시)가 여기서 "이 표는 왜 있나 · 누가 쓰나"를 보여 준다.
   사용자에게는 데이터 설명서·그림(ERD)·성공 기준 결과로 "이렇게 맞나요?" 하고 확인받는다. 모르는 말은 `data-light` 의 `references/guide.md` 처럼 그 사람의 일에 빗대어 한두 줄로.
   표가 여럿이면 웹 그림을 띄워 함께 본다: `python .claude/skills/data-light/scripts/datalight.py view` (브라우저가 열림, 보기 전용,
   표를 끌어 옮기면 위치만 `data/model.light.json.layout.json` 에 -- 이 파일도 저장해 두면 다음에 같은 배치).
5. 확인받으면 고친다: `FEATURES.md` 데이터 절(표 → 쓰는 기능), `NOW.md` "저장하는 데이터"·"개인정보".
   **데이터 검사 장치** -- `NOW.md` `## 설정` 에 `데이터 검사 장치:` 줄이 없거나 `(아직 정하지 않음)` 이면 처음 정본을 저장하기 전에 한 번 묻는다:
   "저장할 때마다 데이터 설계를 자동으로 검사하는 장치를 설치할까요? (추천) 설계가 검사를 통과하지 못하면 저장이 멈춰요."
   - 예 → `datalight.py hook install` -- 커밋 검사 훅(`git config core.hooksPath` 가 있으면 그 폴더), 도구 사본 `.data-light/datalight.py`,
     `.gitignore` 의 **데이터 줄**을 만든다. 인터넷 저장소에 올리지 않는 프로젝트(`## 설정` 의 push 가 `아니오`, 또는 `git remote` 없음)면
     `--no-ci` -- GitHub 검사 파일은 올릴 때만 쓸모가 있다 (도구가 이 선택을 `.data-light/settings.json` 에 기억한다).
     결과에 "이미 있어 건드리지 않았습니다" 가 나오면 다른 검사 훅이 이미 있는 것 -- 사용자에게 알리고, 좋다고 하면 `--append`.
     `hook install` 은 설치한 뒤 이 컴퓨터의 sh 가 훅을 읽는지 스스로 확인하고(`sh -n`), 못 읽으면 우리 블록을 빼고 알린다 (저장을 막는 훅을 남기지 않는다).
     그 알림이 나오면 사용자에게 그대로 전하고 `## 설정` 에 `데이터 검사 장치: 안 함 (이 컴퓨터의 sh 가 훅을 못 읽음)` 으로 적는다.
     그동안 정본을 고친 저장 전에는 `light-check` 가 `verify` 를 직접 돌린다.
   - 아니오 → `안 함`. 이때는 AI 가 `.gitignore` 에 데이터 줄을 직접 더한다 (없는 줄만):
     `data/app.db` `data/backup/` `data/*.csv` `data/*.xlsx` `data/out/spec.xlsx` `data/import_plan*.json` `import_plan*.json` `.env`
     (실제 데이터·원본 파일·가져오기 계획(실제 값 일부가 들어 있다)·비밀 설정은 올리지 않는다. `spec.xlsx` 는 만들 때마다 달라지니 다시 만든다).
   답을 `## 설정` 과 `DECISIONS.md`(`[사용자]`, 답 그대로)에 적는다. 설치했으면 `datalight.py hook status` 가 `결과: 최신` 인지 본다.
   기록하고(아래) `light-save` 로 `데이터:` 저장한다 -- 정본 `data/model.light.json`, `data/out/`, `.gitignore`, 장치를 설치했으면 `.data-light/`
   (와 만들어졌으면 `.github/workflows/data-light.yml`).
6. 실제 DB 만들기(`data/app.db`, Supabase 에 적용)와 파일의 데이터 넣기는 **따로 묻고** 답을 받은 뒤에 한다.
   - 이미 있는 DB 를 바꾸기 전에는 `data/backup/<날짜>-app.db` 로 복사해 둔다 (가져오기는 도구가 스스로 백업한다).
   - 파일 넣기: 파일을 `data/` 안에 두고 프로젝트 맨 위 폴더에서 `datalight.py import plan data/<파일> --table <표>` → 계획은 `data/import_plan.json`
     (경로는 프로젝트 기준으로만, 개인정보 칸의 값은 가려진다 -- 그래도 실제 값 일부가 있어 올리지 않는다) → 칸마다 영어 이름을 채우고
     계획을 표로 보여 주고 확인 → 사용자가 좋다고 하면 계획의 `"approved"` 를 `true` 로 바꾸고
     `import apply data/import_plan.json --model data/model.light.json --db data/app.db --approval "<사용자 답 그대로>"`.
     원본이 프로젝트 밖에 있으면 계획에 파일 이름만 적히므로 apply 때 `--file <위치>`.
     `import apply` 는 SQLite(`data/app.db`) 전용이다 -- 정본이 Supabase(PostgreSQL)면 도구가 멈춘다(`--force-sqlite` 는 쓰지 않는다).
     Supabase 는 계획으로 칸 이름을 맞춘 CSV 를 Table Editor 의 CSV 가져오기로 넣는다 (사용자 확인 후). 자동 번호 칸은 직접 넣을 수 없어서
     ① 본 표의 CSV 를 번호 칸과 개인정보 칸 없이 넣고 ② 매겨진 번호를 Table Editor 에서 확인해(넣은 순서대로) 원본 행과 짝지은 뒤
     ③ 그 번호와 개인정보 칸으로 `pi_` 표의 CSV 를 만들어 넣는다. 실제 값이 든 CSV 는 `data/` 안에만 두고(저장되지 않는다) 다 넣은 뒤 지울지 묻는다.
     실제 저장이 브라우저인 프로젝트도 `import apply` 를 쓰지 않는다 (화면이 읽지 않는 파일에 실제 이름·연락처만 남는다).
   - **Supabase**: `build --db postgresql` 의 SQL 은 **모든 표**에 행 접근 규칙(RLS)을 켜고, 정본의 `access` 대로 실제 규칙(policy)을 만든다
     (위 4). `access` 가 없는 표는 규칙 없이(= 공개용 키로 아무것도 못 함) 틀만 주석으로 남는다 -- 틀을 손으로 쓰기보다 정본에 `access` 를 적는다.
     - `"signup": "closed"` 는 정본에 적는 약속일 뿐 Supabase 설정을 바꾸지 않는다 -- **새 가입 끄기**(Authentication 설정의 "Allow new users to sign up")와
       **익명 로그인 끄기**("Allow anonymous sign-ins" -- 익명 사용자도 로그인한 사람으로 친다)를 사용자에게 부탁하고 **꺼진 것을 확인한 뒤에** SQL 을 적용한다.
       끄지 않았으면 적용하지 않는다.
     - 가입을 끈 사이트의 **계정**은 사용자가 Supabase 의 Authentication → Users → **Add user**(새로 만들기 또는 초대)로 만든다 -- 가입이 꺼져 있어도 된다.
       사이트에는 로그인 화면만 만들고 가입 화면·`signUp` 호출은 만들지 않는다. 사람을 더할 때도 가입을 켜지 않는다 (켜 둔 동안 아무나 가입해 모든 표를 읽는다).
     - 그래도 틀을 손으로 써야 하면 `data/out/schema.sql`(만들어지는 파일 -- 고치면 `verify` 가 실패한다)은 고치지 말고 SQL 편집기에 붙여 넣은 뒤
       주석을 풀어 실행하고, 실행한 SQL 은 `data/supabase-policies.sql` 에 그대로 남겨 저장한다.
     - 적용 전에 규칙을 사용자에게 쉬운 말로 보여 주고("임원 세 분만 로그인해서 모든 표를 보고 고칠 수 있어요"), 적용한 뒤 Supabase 의
       보안 점검(Security Advisor, 도구가 있으면 advisors)에서 RLS·키·익명 로그인 경고가 0인지 본다 (다른 경고는 사용자에게 보여 준다).
     - **이미 만든 Supabase** 에는 `schema.sql` 전체를 다시 실행하지 않는다 (`CREATE TABLE` 이 실패한다) -- 바뀐 부분만 골라 실행한다.
     사이트 코드에는 **공개용 키(anon·publishable)만**, 관리자 키(service_role·`sb_secret_…`)는 절대 넣지 않는다.
7. 다음 단계(화면)로 돌아온다. 코드는 정본의 표·칸 이름을 그대로 쓴다.

이미 DB 가 있으면 (정본 없이 SQLite 파일·Supabase 를 쓰던 프로젝트): 새로 설계하지 않고 **있는 표·칸을 읽어 정본을 만든다**.
SQLite 는 `datalight.py import schema data/app.db` 가 초안 `data/model.light.json` 을 만든다 (이름표는 비어 있다 -- AI 가 채운다).
도구가 내는 `확인:` 줄(규칙에 안 맞는 이름·행을 구별할 칸이 없는 표)은 혼자 고치지 않고 사용자에게 알리고 고르게 한다:
DB 의 이름을 바꾸기(확인 후 백업하고, 그 이름을 쓰는 코드도 함께) / 그 표는 정본 밖에 두기 -- 초안의 `tables` 에서 그 표를 빼고
`"outside": ["log"]` 에 이름을 적는다 (`verify` 의 데이터 보호 검사에서 빠진다, 데이터는 그대로). `FEATURES.md` 에도 적는다. 그 밖에는 DB 를 바꾸지 않는다.
도구가 "개인정보로 보입니다" 라고 한 칸은 사용자에게 맞는지 묻고 `personal` 을 표시한다. `pi_` 표로 옮기는 것은 DB 를 바꾸는 일이라
사용자에게 알리고 확인받은 뒤 백업하고 한다 (그전까지는 `check` 가 막는다고 그대로 말한다).
Supabase 는 AI 가 표 목록을 보고 옮겨 적는다. 만든 정본은 `build` 한 SQL 과 실제 DB 를 비교해 다른 점을 보여 주고 확인받는다.
SQLite 면 `verify --db <파일>` 로 데이터가 든 표·칸이 정본에서 빠지지 않았는지 본다.

기록: 데이터 설계·변경은 기능 칸에 `데이터` 로 남긴다 -- 흐름 `· 기획 · 데이터 · 회원·회비 표 설계 · 확인받음 · 사용자`,
자세히는 `dev-notes/log/데이터/<날짜>.md` (표·칸을 무엇을 더하고 바꾸고 뺐는지, 성공 기준·만들지 않을 것, 사용자 답, verify 결과). 무엇을 위한 것인지는 "무엇을" 칸에.
