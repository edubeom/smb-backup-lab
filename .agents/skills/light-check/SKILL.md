# light-check — 확인하고 끝내기

AI가 "완료했습니다"라고 했는데 열어 보면 안 되는 일을 막는 단계다. **확인하지 않은 것을 확인했다고 말하지 않는다.**

## 1. AI가 직접 확인한다
할 수 있는 것은 전부 실제로 실행해서 확인한다. 머릿속으로 "될 것이다"는 확인이 아니다.

| 확인 | 방법 (가능한 것을 쓴다) |
|---|---|
| 문법 오류 없음 | JS: `node --check 파일.js` · Python: `python -m py_compile 파일.py` · JSON: 파싱해 보기 |
| 페이지가 열린다 | 브라우저 도구가 있으면 실제로 연다. 없으면 로컬 서버(`python -m http.server` 등)를 띄워 응답을 받아 본다 |
| 콘솔 오류 없음 | 브라우저 도구가 있으면 콘솔을 읽는다 |
| 완료 기준 | 카드의 기준을 **하나씩** 실제로 해 본다 (입력·클릭·새로고침). 도구로 못 하면 "사람 확인"으로 넘긴다 |
| 다른 기능 | `FEATURES.md` 의 **모든 기능**을 "확인 방법" 한 줄대로 점검한다. 특히 "영향 받을 수 있는 기능"과 "함께 쓰는 파일" |
| 기능 지도 | 이번에 만들거나 고친 파일이 `FEATURES.md` 의 기능('쓰는 파일')·함께 쓰는 파일·구성에 있는지. `portal_tool.py where "<파일 이름>"` 이 "기능 지도에 없는 파일"을 알려 준다 -- 없으면 지도에 넣는다 (문제가 났을 때 찾을 수 있게) |
| 테스트 | 프로젝트에 테스트가 있으면 실행한다 |
| 설명서 | 카드의 `설명서:` 가 해당 없음이 아니면, 바뀐 장의 **따라 하기를 그대로** 해 본다 (`light-manual`) |
| 데이터 | `data/model.light.json` 이 있으면 아래 "데이터 확인"을 한다 (카드의 `데이터:` 가 없음이어도 -- 다른 기능이 쓰는 표가 그대로인지) |

### 데이터 확인 (짝 스킬 `data-light`)
도구: `python .claude/skills/data-light/scripts/datalight.py` (Codex 는 `.agents/skills/...`, Windows 에서 `python` 이 없으면 `py`).

| 확인 | 방법 |
|---|---|
| 한 번에 (관문) | `datalight.py verify data/model.light.json` -- 설계 검사 + 성공 기준(`goals`) 쿼리 + 규칙 시험(나쁜 값이 막히는지) + `data/out` 이 정본과 같은지 + (옆에 `data/app.db` 가 있으면) 데이터가 든 표·칸이 정본에서 빠졌는지. `결과: 통과` 가 아니면 FAIL 줄을 AI 가 고치고 다시 (사용자에게 고치라고 하지 않는다). **단 "정본에서 빠졌습니다"(DB 의 데이터가 사라질 변경)는 AI 가 고치지 않는다** -- 아래 |
| 검사가 진짜 잡는지 | 정본을 처음 만들었거나 규칙(필수·선택값·가리킴)을 바꾼 작업이면 `verify ... --mutate` -- 규칙을 하나씩 일부러 빼도 잡아내는지 |
| 생성물이 낡았을 때 | verify 가 `out/` 이 다르다고 하면 `datalight.py build data/model.light.json --out data/out` (Supabase 면 `--db postgresql`) 뒤 다시 verify |
| 코드가 정본 이름을 쓰는지 | 이번에 고친 코드의 표·칸 이름을 찾아(`grep`) 정본에 있는지 본다. 없는 이름이 있으면 코드를 고치거나, 정본부터 고친다 (카드로 돌아가 사용자에게 말하고) |
| 실제 DB 가 정본과 같은지 | `data/app.db` 는 verify 가 함께 본다 (데이터가 사라질 변경이면 실패). 정본에 새로 더한 표·칸이 DB 에 아직 없으면 "참고"로 나온다 -- DB 에 더할지는 사용자에게 묻는다. Supabase 는 사용자에게 확인을 부탁한다 |
| 데이터 검사 장치 | `## 설정` 이 `설치함` 이면 `datalight.py hook status` 가 `결과: 최신` 인지 (`훅: 없음` 이면 다른 컴퓨터에서 받은 저장소 -- 사용자에게 묻고 `hook install`, `버전이 다릅니다` 면 `hook install`). 저장할 때 "python 을 찾지 못해 검사를 건너뜁니다" 가 나왔으면 그 저장은 검사되지 않은 것 -- ❓ 로 보고한다. 저장이 `pre-commit` 의 `syntax error` 로 멈추면 이 컴퓨터의 sh 가 훅을 못 읽는 것 -- `hook install` 을 다시 하면 스스로 확인해 못 읽는 블록을 뺀다 (`light-start` "넘겨주는 순서" 5) |
| 만드는 것 | 정본 `product` 가 있고 `said` 가 사용자 말 그대로인지 (AI 가 지어낸 말이 아닌지 -- 처음 답·`DECISIONS.md` 와 비교). `verify` 의 **유형 미정** 은 AI 가 혼자 채우지 않는다 -- 사용자 말이 없으면 묻는다 (`light-resume` 3) |
| Supabase 를 쓰면 | 정본의 `signup`·`access` 가 "누가 쓰나" 답과 맞는지 (정해진 사람끼리 = `closed` + `members`, 아무나 가입 = `open` + owner 칸과 `own`, `pi_` 는 `read` 금지 -- `check` 가 막는 것 말고도 답과 맞는지). `signup: closed` 면 Supabase 의 **새 가입과 익명 로그인이 실제로 꺼져 있는지**(Authentication 설정 -- 정본은 약속일 뿐이다, 사용자에게 화면을 확인받는다), 사이트 코드에 가입 화면·`signUp` 호출이 없는지 (계정은 Supabase 의 Add user 로). `build` 한 규칙이 적용됐는지, 손으로 쓴 틀이 있으면 `data/supabase-policies.sql` 과 같은지. 보안 점검(Security Advisor·advisors)에 RLS·키·익명 로그인 경고가 0인지 (다른 경고는 사용자에게 보여 준다). 코드에 관리자 키가 없는지: `sb_secret_` 로 시작하는 키가 없고, `eyJ` 로 시작하는 키는 가운데 부분(점 사이)을 base64 로 풀어 `"role":"service_role"` 이 아닌지 (이름 `service_role` 로 찾으면 안 나온다). 도구로 볼 수 없으면 사용자에게 화면 위치를 알려 주고 확인을 부탁한다 |
| 올리면 안 되는 것 | `git ls-files` 에 `data/app.db`·`data/backup/`·`data/*.csv`·`data/*.xlsx`·`import_plan*.json` 이 없고 (가져온 원본은 `data/` 에 둔다 -- 사이트가 쓰는 다른 csv 는 괜찮다), `.gitignore` 에 `light-start` 의 "넘겨주는 순서" 5번에 있는 데이터 줄들이 있는지. 정본의 샘플 행이 가져온 실제 값(이름·연락처)이 아닌지 |

- 파이썬이 없으면 `verify` 를 하지 못한다 -- ❓ 확인 못 함에 "데이터 검사 (파이썬 없음)"로 적고, 설치를 부탁하는 방법을 쓴다.
- 정본을 바꾼 작업이면 `FEATURES.md` 데이터 절에서 그 표를 쓰는 **모든 기능**을 "다른 기능" 점검에 넣는다.
- **"DB 의 ... 가 정본에서 빠졌습니다"** 가 나오면 멈추고 사용자에게 고르게 한다 (데이터를 지우는 쪽으로 혼자 고치지 않는다):
  ① 그 표·칸을 설계에 다시 둔다 (데이터 유지) ② 표째로 일부러 설계 밖에 두는 것이면 정본에 `"outside": ["<표>"]` (데이터 유지, 검사에서 빠진다)
  ③ `data/backup/` 에 복사한 뒤 DB 에서도 뺀다 (지워도 된다는 답을 받은 뒤에만)
  ④ 이번 변경을 취소한다. 사용자의 답을 `DECISIONS.md` 에 그대로 남긴다.

## 2. 사람이 확인할 것을 부탁한다
보기 좋은지, 글자가 잘 보이는지, 휴대폰에서 괜찮은지처럼 **사람만 판단할 수 있는 것**은 3개 이내로 콕 집어 부탁한다.
어디를 열고 무엇을 눌러 보면 되는지까지 적는다.

## 3. 결과를 이 형식으로 보고한다
```
확인 결과 -- 작업: <제목>
✅ 확인함
  - 할 일 입력 → 목록에 추가됨 (브라우저에서 직접 입력해 봄)
  - 메모 기능 정상 (메모 쓰고 새로고침 → 남아 있음)
  - 설명서 manual/todo.html 3단계 페이지 그대로 됨 (브라우저에서 순서대로 해 봄)
  - 데이터 설계 정상 (datalight verify 실행: 설계 검사·성공 기준 2개·규칙 확인 OK, 결과: 통과)
👀 직접 확인해 주세요
  - index.html 을 열어 '할 일' 메뉴의 글자 크기가 괜찮은지
❓ 확인 못 함
  - 휴대폰 화면 (브라우저 도구 없음) -- 휴대폰으로 한 번 열어 봐 주세요
```
- **✅ 에는 "어떻게 확인했는지"를 괄호로 반드시 쓴다.** 방법을 못 쓰면 ✅ 가 아니다.
- 완료 기준 중 하나라도 ✅ 가 아니면 "완료"라고 하지 않는다. 남은 것을 말하고 사용자 확인을 기다린다.

## 4. 문제가 나오면
먼저 **왜 안 되는지** 알아본다. 짐작으로 고치지 않는다. 아래 다섯 가지를 확인하고 사용자에게 한 줄씩 말한다:
오류 메시지(처음 나온 오류) · 프로그램·서버 상태 · 최근에 바꾼 것 · 데이터·파일이 바뀌었는지 · 오류 문구 검색 결과.
원인에 따라 길이 다르다. 덮어두고 다음으로 넘어가지 않는다. **같은 방법을 연달아 쓰지 않는다.**

| 원인 | 하는 일 |
|---|---|
| 이번에 고친 것 때문 | 고치고 다시 1번부터 확인. 매번 다른 방법으로, 3번 안 되면 원인을 다시 알아보고 다른 방법(플랜 B)을 사용자에게 말하고 시도. 플랜 B 는 2번까지 |
| 잠깐의 오류 (인터넷 끊김, 프로그램이 아직 켜지는 중, 파일 잠김) | 고칠 것이 없다. 30초 → 2분 → 10분 기다렸다 그대로 다시 (이 세 번이 한 묶음). 그래도 안 되면 다른 방법을 찾고, 없으면 맨 아래 줄로 |
| 다른 서비스·프로그램 문제 | 셋 중 하나: 상태를 직접 볼 수 있으면 지켜보며 기다리기 / 사용자에게 고쳐 달라고 부탁하기 / 내가 고칠 수 있는 곳이면 **먼저 묻고** 고치기. 기다릴 때는 `NOW.md` 지금 작업에 `⏸ 기다리는 중:` 으로 적는다. 기다리기는 3번까지 |
| 내가 할 수 없는 일 (설치·관리자 권한·비밀번호·결정) | 사용자에게 할 일을 그대로 따라 할 수 있게 적어 부탁하고 기다린다. 해 주면 다시 확인 |
| 다른 방법을 못 찾았거나 모두 안 됨 | 사용자에게 셋 중 하나를 고르게 한다: **되돌리기**(light-undo) / **이 기능 빼기**(중요하지 않으면) / **나중에 할 일로 적기**(`NOW.md` 다음에 할 일에 "언제 다시 할지"와 함께) |

- 사용자에게 말할 때: 해 본 방법과 결과, 짐작되는 원인, 다음에 할 일을 쉬운 말로.
- 시도할 때마다 기록한다: 흐름 `· 확인 · <기능> · <무엇을 해 봤나> · 실패 · AI`, 그 기능·날짜 파일의 목록과 자세히(한 일·결과·
  오류 메시지 앞부분·해결 방법) -- 같은 방법을 또 쓰지 않았는지 이 기록으로 확인한다.
- 다른 기능이 망가졌으면 바로 알리고, `FEATURES.md` 에 ⚠️ 로 표시한다.

## 5. 끝나면
사용자가 👀 항목을 확인해 주면(또는 괜찮다고 하면) 카드의 완료 기준을 체크하고 기록한다: 흐름
`· 확인 · <기능> · 완료 기준 N개 · 통과 · 사용자`, 그 기능·날짜 파일의 목록(확인한 것마다 한 줄)과 자세히(어떻게 확인했나·결과).
그리고 `light-save` 로 저장한다.
