# 백업 정책과 실행 계획

## 목표와 범위

리눅스 재설치 후 설정·데이터를 복원하여 서비스를 다시 시작하는 복구를 목표로 한다. 실행 주기는 하루 한 번, 잠정 시각은 **Asia/Seoul 04:00**이다. 최종 서비스별 허용 데이터 손실·복구 소요시간은 첫 시험 결과를 보고 정한다. 일별 백업이므로 마지막 성공 이후 변경은 유실될 수 있으며, 실패가 이어지면 그 기간이 늘어난다.

프로젝트는 Git 이력·미추적 실행 파일·환경 파일·업로드 데이터까지 조사하여 포함한다. 서버는 서비스 구성·네트워크·방화벽·터널·인증서·계정과 권한 복구에 필요한 파일을 포함한다. 컨테이너 writable layer에 영속 데이터가 있는지도 확인한다. 캐시·빌드 산출물은 재생성 가능함을 확인한 항목만 제외한다. 백업 목적지, 임시 덤프, 시험 복원 폴더를 재귀적으로 백업하지 않는다.

PostgreSQL은 DB별 custom format `pg_dump`와 역할·권한 등의 `pg_dumpall --globals-only`를 사용하도록 검토한다. 비밀번호 해시가 포함될 수 있어 결과 전체를 비밀로 취급한다. 실행 중인 PGDATA 단순 복사를 논리 백업 대신 사용하지 않는다. 버전·확장·tablespace 매핑도 남긴다. DB 간 공통 시점 및 업로드 파일과의 일관성은 별도 설계가 필요하며, 쓰기 정지나 서비스 중단이 필요하면 먼저 확인받는다.

메일은 제품을 확인한 후 공식 지원 방식으로 구성·계정·메일함·DKIM·TLS·관련 DB를 함께 확보한다. 실행 중 메일 디렉터리의 단순 복사만으로 성공 처리하지 않는다. 스냅샷·제품 지원 동기화 또는 승인된 점검 시간을 사용한다.

## 공유 공간과 용량 관리

목적지는 `\\192.0.2.1\backup\server`이며 공유기 모델은 ASUS TUF-AX5400이다. 약 900GB는 여러 프로그램의 총 사용 공간이다. 신규 전용 영역 후보는 마운트 후 `/mnt/router-backup/server/g1`로 정정한다. 기존 내용과 실제 여유 공간을 확인하기 전 저장소를 초기화하지 않는다.

첫 전체 백업의 실측 크기·일일 변경량과 다른 프로그램의 사용량으로 G1 예산을 정한다. 독립 일별 아카이브 방식이라면 5개 보존 중 새 백업을 만들 때 최대 6개분과 임시 자료 공간이 필요하다. Restic도 변경 데이터·검사·prune 작업 여유 공간이 필요하다. 공간이 모자라면 **기존 성공본을 먼저 지우지 않고 실패**로 기록한다. G1 범위 밖 자료는 자동 정리하지 않는다. 상한·예비 공간 수치는 공유 인증 후 확정한다.

## 확인된 추가 대상

`inventory.md`의 실행 중 PostgreSQL 16.15뿐 아니라 중지된 PostgreSQL 볼륨 2개, Qdrant 볼륨, `/project/demo-notes/Story.db`, Mailu의 SQLite DB 2개를 처리해야 한다. SQLite는 실행 중 파일 단순 복사 대신 online backup 또는 승인된 정지 상태를 이용한다. Mailu 기존 스크립트는 서비스를 중단하므로 승인 없이 호출하지 않는다. 사용자 지시에 따라 중단 경로를 제거하고 Dovecot/SQLite/Redis 전용 온라인 내보내기로 변경했다. 제품별 시험과 제한은 [메일 수집 문서](mail-online.md)를 따른다. 전체 Mailu 트리에는 `acme`와 `secrets`도 포함한다.

## 도구 선택

Restic은 우선 검토 후보다. Linux CIFS에 대한 공식 호환성 주의가 있어 공유 방식과 커널을 확인하고 시험한 뒤 확정한다. SFTP 등 지원 여부도 조사한다. SMB만 가능하면 로컬에서 암호화한 독립 일별 아카이브를 만들고 임시 이름으로 전송한 뒤 검증·완료 표시하는 방법을 비교한다. 이 경우 여유 공간, 전송 중단, 대용량 파일 제한, POSIX 소유권·ACL·xattr 복원을 시험해야 한다.

## 1회 실행의 성공 조건

1. 단일 실행 lock을 획득한다. 예상 호스트인지 확인한다.
2. 공유 mount의 정확한 mount point·source·파일시스템·전용 저장소 식별자를 검증한다. 단순 디렉터리 존재만 확인하지 않는다. 미마운트·다른 디스크·읽기 불가·공간 부족이면 실패하고 로컬 빈 mount 폴더에 기록하지 않는다.
3. 로컬/공유 공간을 확인하고, root 전용 실행별 임시 폴더에 DB·메일의 일관된 내보내기와 비밀 없는 버전 목록을 만든다. 평문 임시 자료 접근을 제한한다.
4. 원본 읽기 누락, DB/메일 내보내기 실패, 전송 실패는 모두 전체 실패로 처리한다. 부분 스냅샷은 보관 대상 성공 목록에서 제외한다.
5. 암호화 백업을 공유기에 저장한다. 저장소 무결성 검사와 해당 실행 데이터 읽기 검증을 수행한다. 아카이브 방식은 전송 해시와 복호화·목록/추출 검증을 수행한다. 첫 실행은 전체 데이터를 읽어 검증한다.
6. 검증 통과 후에만 실행 ID·한국 날짜·snapshot ID·완료 시각·검증 결과를 원자적으로 성공 목록에 기록한다. 민감한 파일명·자격증명은 로그에서 제외한다.
7. 기존 성공 백업 삭제는 승인된 정책이 있을 때만 수행한다. 실패·중단 시 기존 성공 백업은 유지한다. 임시 자료는 완료/실패 정책에 따라 안전하게 정리하며 민감한 원문은 Git 밖에 둔다.

## 최근 성공 일별 백업 5개

한국 날짜마다 검증된 성공본 하나를 대표로 정하고, 성공한 날짜 기준 최근 5개를 남긴다. 실패한 날은 숫자에 포함하지 않는다. 같은 날 재시도 성공도 일별 보관 수를 늘리지 않는다. 초기에는 5개 미만을 그대로 보관한다.

Restic의 단순 `--keep-daily 5`만으로 외부 검증 성공을 판별할 수 없다. 검증된 성공본 전용 태그/목록과 날짜 기준을 구현하고 host/path/tag 그룹 분리로 보관 수가 예상과 달라지지 않는지 dry-run으로 검증한다. 구현 시점에 설치 버전의 시간대 동작도 확인한다. 실패 스냅샷은 성공 목록에서 제외하고, 삭제할 경우 따로 목록을 제시한다.

**첫 정리 전 삭제 예정 snapshot/날짜와 보존 5개를 보여 주고 사용자 승인을 받는다.** 반복 자동 정리의 범위까지 승인받기 전에는 forget/prune/기존 파일 삭제를 활성화하지 않는다. 기존 백업은 새 저장소 보관 정책 대상에 포함하지 않는다.

## 단계별 완료 기준

1. G1 접속·신원 확인 후 읽기 전용 조사 완료. 실제 경로·용량·기존 스케줄·복구 의존성 확정.
2. 공유기 모델·공유 방식·용량 확인. 기존 자료 목록 조사 후 새 전용 경로 확정. 비밀은 서버 파일로 설치하고 암호화 복구 키는 G1 외부의 안전한 장소에도 보관.
3. 도구·스크립트·systemd service/timer 구현. mount 오인·동시 실행·덤프 실패·공간 부족·전송 중단·검증 실패 때 성공 표시와 삭제가 발생하지 않는지 시험.
4. 자동 정리 비활성화 상태로 첫 수동 백업. 서비스 중단이 필요한 경우 먼저 승인. 전체 읽기 검증·로그 확인. 이 단계에서 기존 백업을 삭제하지 않음.
5. 별도 임시 경로와 격리 DB/메일 환경에서 복구 시험. `restore.md`의 판정 기준과 소요시간 기록. 불일치가 있으면 백업 절차 수정 후 재시험.
6. 한국 시간 매일 04:00 timer 활성화. `Persistent=true` 사용 시 누락 실행은 부팅 후 보충하되 같은 날짜 중복 실행을 방지하고 여러 누락 날짜를 가짜 성공본으로 채우지 않음. 실패와 최근 성공일을 journal/상태 파일로 확인 가능하게 구성. 알림 채널은 추후 확정.
7. 보존 5개가 쌓이면 정리 dry-run을 사용자에게 제시하고 승인 범위 내에서 활성화. 정기 복구 시험은 월 1회 제안, 비용/용량 확인 후 운영에 반영.

## 사용자 추가 요구 반영

SSH·Cloudflare 등 /etc 전체와 사용자 홈의 운영 설정을 별도 구성요소로 수집한다. /project는 프로젝트별 tar 및 암호화 파일로 분리한다. 새 objects-v2의 여러 파일은 전부 검증된 뒤 하나의 일별 성공으로 기록하며 기존 bundle-v1을 변환/삭제하지 않는다. 자세한 구조는 [백업 파일 구성](backup-layout.md)을 따른다.
