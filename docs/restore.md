# 복구 절차와 첫 시험

1차 조사에서 Mailu 2024.06과 실행 중 PostgreSQL 16.15를 확인했다. 중지된 DB 및 세부 설정의 추가 조사가 필요한 절차 초안이다. 현재 상태에서 운영 복원 명령으로 사용하지 않는다. 시험 대상 백업 ID를 고정하고 운영 데이터 덮어쓰기를 금지한다.

## 첫 복구 시험

1. 공유기에 저장한 첫 성공본을 선택하고 G1 외부에 보관한 키로 열 수 있는지 확인한다. 로컬 원본 덤프를 재사용하지 않고 공유기에서 읽어 시험한다.
2. 충분한 공간의 root 전용 빈 시험 폴더에 파일을 복원한다. 권한·UID/GID·symlink·ACL·xattr와 대표 파일의 내용을 백업 시점 manifest와 비교한다. .env/키는 값 출력 없이 존재·권한·해시만 검증한다. 필요 비밀은 시험 환경으로 제한적으로 전달한다.
3. 운영과 분리한 PostgreSQL 인스턴스를 호환 major와 동일 확장으로 만든다. 다른 데이터 볼륨·포트를 사용하고 운영 네트워크에 연결하지 않는다. globals를 검토해 시험용 계정/권한으로 복원한 뒤 모든 DB를 복원한다. 복원 오류 0건, 스키마·확장·권한·시퀀스·핵심 데이터와 애플리케이션 읽기 기능을 확인한다. 비교 기준은 live 서버의 현재 값이 아닌 백업 시점 자료를 사용한다.
4. 동일 버전 메일 서비스를 격리 환경에서 구성한다. 외부 SMTP 송신·수신, 자동 전달, DNS·터널 연결을 차단한다. 시험 계정 로그인, 폴더·메일 수 및 대표 첨부파일 읽기를 확인한다. DKIM·TLS 파일도 권한 포함 복원 여부를 확인한다.
5. 앱을 시험 DB와 업로드 경로로 시작하고 로그인·조회·대표 업로드 읽기를 확인한다. 결제·웹훅·메일 발송·예약 작업 등 외부 부작용을 차단한다.
6. 백업 ID, 도구/서비스 버전, 검사 항목, 성공·실패, 데이터 시점, 복구 소요시간·공간, 남은 제약을 비밀 없이 기록한다. 운영 서비스가 변경되지 않았는지 확인한다. 시험 중 생성한 민감 자료는 Git 밖에서 관리하고 시험 후 정리한다.

첫 복구 시험 전에는 “복구 가능 검증 완료”로 표시하지 않는다. 백업 파일 읽기 검사와 서비스 복구 시험 결과는 각각 기록한다.

## 실제 장애 시 복구 순서

1. 장애 원인과 디스크 상태를 확인한다. 운영 데이터 덮어쓰기·서비스 중단이 필요한 작업 목록을 제시하고 사용자 확인을 받는다. 복구 원본과 최신 성공 ID를 선택한다.
2. 대체 OS·디스크·네트워크·관리자 SSH를 준비한다. 공유기 접근 정보와 외부 보관 복구 키를 확보한다.
3. 암호화 저장소를 검사하고 안전한 임시 경로로 복원한다. 패키지·컨테이너 이미지 버전, 계정 UID/GID, 파일 소유권·권한을 재현한다. 네트워크 설정은 대체 장비에 맞게 검토한다.
4. 외부 트래픽·자동 작업을 차단한 상태로 DB를 복원하고 계정/권한·확장·tablespace를 확인한다.
5. 메일 계정 DB·메일함·구성·키를 해당 제품 절차와 순서로 복원한다. 프로젝트·업로드·환경 설정을 복원한다.
6. 의존 서비스 → DB → 앱/메일 → 프록시/터널 순서를 실제 구성에 맞게 확정하여 시작한다. 로컬 검증 후 사용자 확인된 전환 절차에 따라 외부 연결을 연다. 중복 메일 송신이나 cron 실행을 방지한다.
7. 외부에서 접속·메일 송수신을 점검하고 정상 백업 일정을 재개한다. 실패 시 외부 연결을 차단하고 원본을 보존한 채 이전 성공본 또는 대체 환경으로 되돌린다.

실제 실행 명령·서비스명·메일 복원 순서는 현황 조사 후 추가한다. OS 전체 부팅 이미지 복원은 이 계획의 범위 밖이다.

## 1차 조사에 따른 구체화

- 실행 PostgreSQL 시험은 16 major와 확인한 모든 DB를 대상으로 한다. 중지된 postgres:15-alpine은 별도 호환 인스턴스로 다루며 같은 데이터 디렉터리를 공유하지 않는다. 원본 볼륨을 시험 인스턴스에 연결하지 않는다.
- Mailu는 `/project/demo-mail` 구성, main.db, roundcube.db, 메일함·계정/웹메일 DB·DKIM·TLS·Redis와 사용자 override를 함께 복원한다. 인증서 갱신은 사용자 systemd timer와 acme 설정까지 재현한다.
- Story.db는 별도 복원해 SQLite 무결성과 앱 읽기 기능을 검사한다. Qdrant도 보존 대상으로 확정되면 별도 볼륨에서 컬렉션·검색 기능을 검증한다.
- 기존 메일 백업 스크립트는 서비스를 중단하므로 복구 시험 준비에도 실행하지 않는다.

[Mailu 2024.06 공식 유지보수·이전 절차](https://mailu.io/2024.06/maintain.html)는 쓰기가 멈춘 최종 동기화 단계를 포함한다. 현재는 사용자 결정에 따라 중단하지 않고 Dovecot/SQLite/Redis 전용 내보내기로 분리한다. 전체 공통 시점과 수집 중 SMTP 대기열을 보장하지 않는 제한은 [메일 온라인 수집·복구](mail-online.md)에 적었다. 단순 live 파일 복사로 대체하지 않는다.

## 프로젝트별 파일 형식 업데이트

최신 objects-v2는 프로젝트별 `files.tar.gz.gpg`, DB별 export, 시스템 설정 파일을 독립적으로 보관하고 하루 성공 기록 하나로 관리한다. `--snapshot ... --project demo-web` 또는 `--component system/etc.tar.gz`로 선택 복원한다. 명령·경로·적용 주의는 [프로젝트별 백업 안내](backup-layout.md)를 따른다. 예전 bundle-v1 백업은 기존 --archive 방식으로 복원한다. 첫 실행은 관리 프로젝트/SSH/Cloudflare 파일과 메일 SQLite 무결성/격리 우편함 읽기를 확인했으며 PostgreSQL·메일의 격리 서비스 복원 시험은 여전히 별도로 수행해야 한다.

## 첫 백업 후 PostgreSQL 실제 복구 시험

첫 전체 백업 성공은 [실행 기록](first-backup-result.md)에 남겼다. 공유기 성공본 ID를 고정하고 [PostgreSQL 복구 도구](postgres-restore-test.md)를 실행한다. 이 도구는 원본 역할·소유권·ACL을 보존해 새 컨테이너에서 복원하고 조회하며 실제 G1 저장소 크기도 보고한다. PostgreSQL/Mailu 전체 서비스 복구 및 자동 실행 완료는 각각 실제 결과 이후에 기록한다.

## 실제 PostgreSQL 결과와 키 보관 상태

첫 성공본의 5개 DB 실제 복원·읽기와 전체 cipher hash 재검증은 [사용자 결과](postgres-restore-result.md)로 확인했다. 컨테이너 상태 불변·공개 포트/운영 볼륨 사용 없음이다. 외부 보관 키의 재입력·공유기 명세 복호화도 [결과](recovery-key.md)로 통과했다. Mailu 전체 서비스/앱 업무 기능/보존 볼륨 복구는 별도이며 일일 예약과 명시 범위의 정리 정책은 사용자17:28 승인·활성화됐지만 첫 예약 성공과 재부팅 연결은 아직 미검증이다.
